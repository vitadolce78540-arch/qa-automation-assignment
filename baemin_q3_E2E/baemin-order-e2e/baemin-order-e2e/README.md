# 문제3. 주문 플로우 E2E 리뷰 / 리팩토링

원본 테스트(Kotlin + UIAutomator)를 리뷰하고 Appium + Java로 다시 작성했습니다.
설계 의도를 보여 드리는 용도로 봐 주시면 감사하겠습니다.

## 1. 원본 코드 문제점

```kotlin
@Test
fun testOrderFlow() {
    val shopItem = device.wait(Until.findObject(By.textContains("치킨")), 5000)
    shopItem.click()
    val menuItem = device.wait(Until.findObject(By.textContains("후라이드")), 3000)
    menuItem.click()
    val orderBtn = device.wait(Until.findObject(By.textContains("주문하기")), 3000)
    orderBtn.click()
    val payBtn = device.wait(Until.findObject(By.textContains("결제")), 3000)
    payBtn.click()
    Thread.sleep(5000)
    val statusText = device.wait(Until.findObject(By.textContains("접수 대기")), 3000)
    Assert.assertNotNull(statusText)
}
```
한 줄로 정리하면 "정해진 시간만큼 기다리고, 글자 일부로 찾고, 마지막에 글자가 보이면 통과"하는 테스트입니다.
실패하면 왜 실패했는지 알기 어렵고, 통과해도 정말 주문이 제대로 됐는지는 알 수 없습니다.

### 안정성

- 대기 시간(5초, 3초)에 근거가 없습니다. CI 에뮬레이터가 느리거나 네트워크가 조금만 늦어도 실패하고, 환경별로 한 번에 조정할 방법도 없습니다.
- 결제 후 `Thread.sleep(5000)`은 승인이 5초를 넘기면 실패하고, 빨리 끝나도 5초를 그냥 버립니다. 실무에서 Flaky가 나는 가장 흔한 패턴입니다.
- `device.wait()`는 못 찾으면 null을 돌려주는데 바로 `click()`을 호출합니다. 결과는 NPE 하나뿐이라 어느 화면에서 뭘 못 찾았는지 남지 않습니다.
- `textContains`는 부분 일치라 엉뚱한 요소가 잡힙니다. "치킨"은 배너·광고·가게명, "후라이드"는 양념반후라이드반, "결제"는 결제수단·간편결제 라벨까지 걸립니다. 먼저 그려진 걸 누르기 때문에 실행할 때마다 다른 곳을 누를 수 있습니다.
- 요소가 보이기만 하면 바로 누릅니다. 화면 전환 애니메이션 중이거나, 버튼이 아직 비활성이거나, 이벤트/쿠폰 팝업이 덮고 있으면 클릭이 씹히거나 다른 게 눌립니다.
- 스크롤 처리가 없어서 메뉴가 화면 밖에 있으면 못 찾습니다. 필수 옵션이 있는 메뉴는 옵션을 안 고르면 버튼이 비활성이라 그대로 멈춥니다.
- 시작 전 상태를 맞추지 않습니다. 로그아웃 상태, 배달 불가 지역, 이전 실행에서 남은 장바구니("장바구니 교체" 팝업), 야간 영업 준비중 등 실행 시점에 따라 결과가 달라집니다.

### 유지보수성

- 화면 이동, 조작, 대기, 검증이 한 메서드에 다 들어 있습니다(Page Object 없음). 장바구니 화면 하나만 바뀌어도 그 화면을 지나는 테스트를 전부 찾아 고쳐야 합니다.
- 화면 문구로 요소를 찾아서 문구 변경, A/B 테스트, 다국어 적용 때마다 깨집니다. 기능은 정상인데 테스트만 빨간 경우가 쌓이면 결국 아무도 결과를 안 보게 됩니다.
- 대기 시간과 문자열이 코드 곳곳에 하드코딩되어 있습니다.
- `testOrderFlow`라는 이름으로는 무엇을 보장하는 테스트인지, 어디까지가 준비이고 어디부터가 검증인지 알기 어렵습니다.

### 신뢰성

- 마지막 검증이 화면 어딘가에 "접수 대기" 글자가 있는지뿐입니다. 이전 주문 내역이나 알림에 같은 글자가 있으면 이번 주문이 실패해도 통과합니다.
- 중간 검증이 없어서 다른 가게, 다른 메뉴, 잘못된 금액으로 주문해도 끝까지만 가면 통과합니다. 반대로 앞에서 생긴 문제가 뒤에서 터져 원인 위치를 찾기 어렵습니다.
- "접수 대기"는 금방 지나가는 상태입니다. 가게가 빨리 받으면 "조리 중"으로 바뀌어 앱은 정상인데 실패합니다.
- 상용 데이터(노출 순서, 광고, 품절)에 따라 결과가 달라져 재현이 어렵습니다.
- 실패해도 스크린샷, 화면 구조, 로그가 남지 않아 CI 실패를 추측으로 분석해야 합니다.

### 운영 리스크

- 결제수단을 지정하지 않아서 계정 기본 결제수단으로 실제 결제가 될 수 있습니다.
- 생성된 주문을 취소하지 않습니다. 실제 가게에 주문이 들어가고, 돌릴 때마다 쌓여서 다음 실행과 통계/정산에 영향을 줍니다.

## 2. CI에서 Flaky가 나면 확인하는 순서

재시도로 일단 통과시키기 전에 어디서, 언제, 왜 실패했는지부터 봅니다. 테스트 문제일 수도 있지만 실제 사용자도 가끔 겪는 결함일 수도 있어서입니다.

1. **실패 패턴 모으기**
   CI 이력에서 실패율, 실패 단계, 단말/OS, 시간대, 같이 실패한 테스트를 정리합니다. 특정 단계나 단말, 시간대에 몰려 있으면 거기서부터 봅니다.
2. **실패 시점 자료 보기**
   스크린샷과 화면 XML로 화면 자체가 다른지(팝업, 로딩, 다른 화면), 요소가 다른지(ID/문구 변경), 값이 다른지(금액, 상태)를 나눕니다. logcat에서 crash, ANR, 네트워크 오류, 결제 SDK 오류도 확인합니다.
3. **환경 확인**
   그 시각에 QA 서버 배포·장애·점검이 있었는지, 에뮬레이터 CPU/메모리, 애니메이션 설정, 네트워크, 같은 테스트 계정을 다른 Job이 동시에 썼는지 봅니다. 환경 문제면 테스트가 아니라 CI 쪽을 고칩니다.
4. **테스트 데이터 확인**
   테스트 가게 영업 여부·자동 접수 설정, 메뉴 품절, 장바구니 잔여, 정리 안 된 이전 주문, 테스트 결제수단 만료/한도를 봅니다. 이전 실행에서 정리가 실패한 적이 있으면 이번 실패와 연결되는지도 확인합니다.
5. **테스트 코드 동기화 점검**
   대기 조건이 충분한지, 애니메이션 중 클릭은 없는지, 화면 갱신으로 요소가 바뀌지 않았는지, 셀렉터가 여러 개에 걸리지 않는지, sleep이 남아 있지 않은지 봅니다. 시간이 부족해 보여도 바로 늘리지 않고, 뭘 기다려야 하는지(로딩 종료, 버튼 활성화)부터 바로잡습니다.
6. **제품 결함인지 확인**
   여기까지 설명이 안 되면 앱/서버를 의심합니다. 서버 로그와 주문 데이터를 맞춰 보고(상태 반영 지연, 중복 주문 등), API로 같은 시나리오를 반복해 UI 없이도 재현되면 결함으로 올립니다.
7. **반복 실행으로 재현율 측정**
   CI와 같은 단말 이미지에서 수십 번 돌려 실패율을 숫자로 남깁니다. 네트워크 지연, CPU 제한, 애니메이션 켜기 같은 조건을 하나씩 바꿔 가며 실패율이 오르는 조건을 찾습니다.
8. **조치 / 재발 방지**
   고친 뒤 같은 방식으로 반복 실행해서 실패율이 0에 가까운지 확인하고 배포 게이트에 다시 넣습니다. 원인을 찾는 동안에는 격리 스위트로 빼서 배포는 막지 않되, 실행은 계속해 데이터를 모으고 해당 흐름은 수동으로 확인합니다. 원인은 코드/데이터/환경/결함으로 분류해 기록하고, 같은 유형이 반복되면 개별 테스트보다 공통 코드나 환경을 고칩니다.

## 3. 리팩토링 시나리오

요청받은 흐름 그대로 작성했습니다.

1. 앱 실행, 타임세일 팝업이 뜨면 X로 닫기
2. 음식배달 > 더보기 > 치킨 (치킨이 안 보이면 메뉴 전체보기에서 치킨 선택)
3. 목록에서 첫 번째로 보이는 가게 진입
4. 첫 번째 메뉴 선택, 필수 옵션 있으면 선택
5. 장바구니 담기 > 장바구니 확인
6. 주문하기 > 결제 화면 진입
7. 결제 화면 확인 후 종료

결제 버튼은 누르지 않습니다. 

단계마다 넘어가기 전에 확인하는 것들:

- 팝업은 X를 누른 뒤 실제로 사라졌는지까지 확인
- 치킨 목록은 치킨 탭이 선택된 상태인지 확인 (가게 카드가 보인다고 치킨 목록이라는 보장은 없어서)
- 목록에서 읽어 둔 가게명/메뉴명이 다음 화면에서도 같은지 확인
- 장바구니는 수량 1, 주문 금액이 담기 금액 이상인지 확인
- 결제 화면은 결제수단 영역, 결제 금액이 장바구니 금액과 같은지, 결제 버튼이 활성 상태인지 확인

이번 시나리오는 "첫 번째 가게의 첫 번째 메뉴"라서 기대값을 미리 정할 수 없습니다. 그래서 앞 화면에서 읽은 값을 `OrderDraft`에 담아 두고 뒤 화면에서 비교하는 방식으로 했습니다.

## 4. 코드 구조

```
src/test/java/baemin/order/
├── Baemin_Order_E2E_Test.java    시나리오
├── base/BaseDriver_Baemin.java   세션 Rule, PASS 출력, 결과 CSV
├── core/
│   ├── Config.java               UDID, Appium 주소, 패키지 등 (-P로 주입)
│   ├── Timeouts.java             용도별 대기 시간 + 배율
│   ├── Target.java               요소 이름 + 찾는 방법(후보 여러 개)
│   ├── Ui.java                   조건 대기, 클릭, 스크롤, 폴링
│   ├── DriverSessionRule.java    세션 생성/종료, 실패 시 스크린샷·XML·logcat 저장
│   └── Log.java                  "-----단계명" 로그, 실패 단계 기록
└── pages/                        화면별 Page Object
    BasePage, TimeSalePopup, HomePage, FoodDeliveryPage, AllMenusPage,
    StoreListPage, StorePage, MenuDetailPage, CartPage, CheckoutPage, OrderDraft
```

Page 객체는 생성될 때 해당 화면에 도착했는지를 먼저 확인합니다. 홈의 "음식배달" 버튼처럼 두 화면에 같은 문구가 있는 경우에는 이전 화면이 사라졌는지도 같이 봅니다.

## 5. 로케이터

배민 앱은 대부분 Compose 화면이라 resource-id가 거의 없고 content-desc로 노출됩니다. 그래서 요소마다 후보를 여러 개 두고 먼저 보이는 걸 쓰게 했습니다.

실기기(S24 Ultra, Android 17)에서 직접 확인한 값:
패키지 `com.sampleapp`, 액티비티 `com.baemin.presentation.ui.root.ui.RootContainerActivity`, 실행 직후 뜨는 인앱 메시지 `com_braze_inappmessage_html`, `하단탭바 홈탭`, `음식배달에서 더보기`, `장바구니`, 홈 가게 카드 `총 N개 가게 중 N번째`

아직 확인 못 한 값(코드에 `[확인 필요]`로 표시):
타임세일 팝업 X 버튼, 음식배달/메뉴 전체보기 화면 제목, 치킨 탭 선택 상태, 가게 상세·메뉴 항목, 담기/주문하기/결제하기 버튼 문구, 필수 옵션 배지, 장바구니 전체삭제

실 수행이 필요할 경우 확인 필요 항목은 첫 실행 전에 Appium Inspector로 보고 각 Page 클래스 위쪽 상수만 고치면 됩니다. 시나리오 코드는 손댈 필요 없습니다.

## 6. 실행 방법

준비: JDK 17+, Node.js, Android SDK(adb), USB 디버깅 켠 단말
테스트 계정은 로그인과 배송지 설정이 되어 있고, 자동 적용 쿠폰이 없어야 합니다(결제 금액 비교 때문).

```bash
npm install -g appium
appium driver install uiautomator2
appium                      # Appium 2는 /wd/hub 경로 없음

adb devices                 # 단말 ID 확인

./e2e_automation test -Pudid=<단말 ID>
./e2e_automation test -Pudid=<단말 ID> -Ptimeout.scale=1.5 -Presult.csv=C:/PP_CSV/baemin_order.csv
```

Windows는 `e2e_automation.bat test -Pudid=<단말 ID>` 로 실행합니다. (Gradle Wrapper 스크립트 이름만 바꾼 것이라 사용법은 gradlew와 같습니다.)

자주 쓰는 옵션:

- `udid` : 단말 ID (없으면 Appium이 알아서 고름)
- `appium.server` : 기본 `http://127.0.0.1:4723`
- `timeout.scale` : 대기 시간 배율, 느린 장비면 1.5~2
- `result.csv` : 결제 화면 진입 시간을 누적 기록할 파일
- `artifacts.dir` : 실패 자료 저장 위치, 기본 `build/test-artifacts`
- `cleanup.cart` : 테스트 후 장바구니 비우기, 기본 true

실패하면 `build/test-artifacts/<테스트명>_<시각>/` 아래에 failure.txt(실패 단계, 액티비티, 원인), screen.png, hierarchy.xml, logcat.txt가 남습니다.

## 7. 작업 방식 및 AI 활용

원본 코드 분석과 시나리오·설계 방향은 직접 정하고, 코드 작성은 AI 도구(Anthropic Claude)를 활용했습니다.

| 영역 | 담당 | 내용 |
| --- | --- | --- |
| 문제점 분석 | 본인 | 안정성·유지보수성·신뢰성 관점 분석을 정리하고 최종 문장은 직접 다듬음 |
| 시나리오 정의 | 본인 | 앱 실행 → 타임세일 팝업 닫기 → 음식배달 더보기 → 치킨(없으면 메뉴 전체보기) → 첫 가게 → 메뉴 → 주문 → 결제 화면 흐름 정의 |
| 설계 방향 | 본인 | Appium + Java 선택, 기존에 운영하던 E2E 스크립트 구조(공통 Base 클래스 상속, 단계 로그, 진입 시간 측정) 유지 요청 |
| 실기기 확인 | 본인 + Claude | 실기기를 연결해 패키지·액티비티와 홈 화면 요소를 확인하고 로케이터 설계에 반영 |
| 테스트 코드 | Claude | Page Object, 조건 기반 대기, 단계별 검증, 실패 아티팩트 저장 코드 작성 |
| 문서 | 본인 + Claude | README 초안은 Claude 로 작성하고 내용 검토·수정 |

실행 환경이 없어 단말에서 끝까지 실행하지는 못했습니다. 실기기에서 확인하지 못한 로케이터는 코드에 `[확인 필요]`로 표시했습니다.
