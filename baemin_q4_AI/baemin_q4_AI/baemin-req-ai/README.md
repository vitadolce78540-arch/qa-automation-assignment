# 문제4. 요구사항 인입부터 영향 범위 테스트 실행까지 AI 자동화

## 무엇을 만들었나

신규 요구사항(기획서 변경)이 들어오면 아래 과정을 한 번에 돌리는 도구입니다.

1. 기획서에서 바뀐 문장만 뽑는다
2. 바뀐 문장을 내부 정책과 대조해 요구사항으로 정리한다 (정책 충돌, 정책에서 파생되는 조건 포함)
3. 기획·정책 근거가 달린 TC 를 만든다
4. 이번 변경 때문에 다시 돌려야 할 기존 자동화 스크립트를 고른다
5. 신규 TC 는 AI 에이전트가 앱에서 직접 수행하고, 통과한 것은 회귀 스크립트로 바꾼다
6. 기존 스크립트와 새 스크립트를 실행하고, 실패를 "결함 의심"과 "기획 변경으로 스크립트 갱신 필요"로 나눠 보고한다

시나리오는 모두 가상입니다. 배달 앱의 실시간 주문 현황 화면 기획서 v1 → v2, 가상의 주문·쿠폰·결제 정책서, 가상 앱 화면으로 구성했습니다.

## 왜 이렇게 설계했나

요구사항이 들어올 때 QA 가 실제로 시간을 쓰는 곳은 세 군데입니다.

- 기획서에는 없지만 정책상 지켜야 하는 조건 찾기 (쿠폰은 주문당 1장, 취소는 5분 이내 같은 것)
- 그 조건까지 포함한 TC 작성
- 이번 변경으로 기존 자동화 중 무엇이 영향을 받는지 판단하고, 깨진 스크립트가 결함인지 기획 변경 때문인지 구분하기

AI 는 앞의 두 가지를 빠르게 해 주지만 없는 정책 조항을 만들어 내거나, 기획서에 없는 기대값을 섞어 넣습니다. 그래서 원칙을 하나 정했습니다.

**LLM 은 정리하고 고르는 일만 하고, 맞는지 판정은 코드가 한다.**

| 단계 | LLM | 코드 |
| --- | --- | --- |
| ① 변경점 | - | 이전/새 기획서 문장 단위 비교 |
| ② 요구사항 | 변경 문장을 요구사항으로 정리 | 근거 문장이 기획서에 실제로 있는지 |
| ③ 정책 대조 | 근거/제약/충돌 판단, 파생 조건 작성 | 관련 조항 검색, 인용한 조항·문구가 정책서에 실제로 있는지 |
| ④ TC | TC 작성 | 근거 확인, 요구사항·정책 조항별 TC 누락, 모호한 기대결과 |
| ⑤ 영향 분석 | 태그로 안 잡히는 연관 스크립트 추천 | 태그·정책 조항 매칭, 추천 스크립트 실재 확인 |
| ⑥ 실행 | 누를 요소, 확인할 요소 선택 | 화면에 있는 요소인지, 위험 동작인지, 기대값 비교 |

LLM 에 기획서 전체나 정책서 전체를 넘기지 않습니다. 바뀐 문장과, 코드가 검색한 관련 조항만 넘깁니다. 이미 검증한 부분까지 TC 가 다시 나오는 걸 막고, 없는 조항을 지어낼 여지를 줄이기 위해서입니다.

## 동작 구조

```
기획서 v2 등록 (Jira / 위키 변경 이벤트)
   │
   ▼
① 변경점 추출 (코드) ──────────── v1 ↔ v2 문장 비교 → 추가·변경·삭제 문장
   │
   ▼
③ 정책 검색 (코드) ───────────── 변경 문장마다 관련 정책 조항 후보
   │                             (정책 섹션 이름 매칭 + 글자 2-gram 유사도)
   ▼
② 요구사항 분석 + 정책 대조 (LLM) ─ 요구사항, 정책 근거/제약/충돌, 파생 조건, 기획 확인 질문
   │
   ▼
④ TC 생성 (LLM) → 검증 (코드) ──── 기획·정책 근거 확인, 커버리지, 모호 표현
   │
   ├──────────────────────────────┐
   ▼                              ▼
⑤ 영향 분석                       ⑥ 신규 TC 실행 (AI 에이전트)
   기존 스크립트 메타데이터           화면 요소 목록을 보고 한 단계씩 조작
   (기능 태그, 정책 조항, 검증 문구)    가드레일: 없는 요소 거부, 결제·취소 차단, 반복 감지
   와 매칭 + LLM 추천                 기대값 비교는 코드가
   │                              │ PASS → 회귀 스크립트 변환 → 코드 게이트
   ▼                              ▼
기존 스크립트 실행 ──────────── 신규 스크립트 실행
   │
   ▼
리포트 (Jira 코멘트): 변경점, 정책 이슈, TC, 누락, 영향 스크립트, 실행 결과와 실패 분류
```

### 단계별로 신경 쓴 부분

**① 변경점 추출**
섹션별로 문장을 나눈 뒤 비교합니다. 바뀐 구간 안에서 비슷한 문장끼리는 "변경"으로 짝짓고, 나머지는 추가·삭제로 봅니다. "가게 확인 중 → 도착 시간 계산 중"이 삭제+추가가 아니라 변경으로 잡혀야, 뒤에서 기존 스크립트의 기대값이 바뀐 것을 찾을 수 있습니다.

**③ 정책 검색과 대조**
처음에는 글자 유사도로만 검색했는데, "쿠폰을 여러 장 적용"과 "쿠폰은 주문당 1장만"이 같은 주제인데도 잡히지 않았습니다. 그래서 문장에 정책 섹션 이름(쿠폰, 주문 취소 등)이 있으면 그 섹션 조항을 모두 후보로 넣도록 했습니다. 조항이 많아지면 임베딩 검색으로 바꾸면 되고, 인터페이스는 그대로입니다.

LLM 은 조항마다 관계를 정합니다.

- 근거: 기획과 같은 내용
- 제약: 기획서엔 없지만 지켜야 하는 조건
- 충돌: 기획이 정책과 어긋남

제약에서는 경계·예외 TC 가 나오고, 충돌은 TC 를 만들지 않고 기획 확인 항목으로 올립니다.

**④ TC 검증**
TC 의 근거는 기획 문장이거나 정책 조항이어야 하고, 둘 다 원문과 문자열로 대조합니다. 커버리지는 두 가지로 봅니다. 요구사항마다 TC 가 있는지, 그리고 요구사항에 걸린 정책 조항(근거·제약)마다 그 조항을 검증하는 TC 가 있는지입니다.

**⑤ 영향 분석**
기존 스크립트마다 메타데이터를 둡니다 (`samples/regression/registry.json`).

- 기능 태그
- 관련 정책 조항
- 스크립트가 검증하는 문구

요구사항의 태그나 인용 조항이 겹치면 선정합니다. 스크립트가 검증하는 문구가 변경 "전" 기획 문장에 있으면 "기대값 변경 예상"으로 표시합니다. 이 스크립트가 실패하면 결함이 아니라 스크립트 갱신 대상으로 분류합니다.

**⑥ 실행**
에이전트에는 스크린샷 대신 화면 요소 목록(e1, e2…)을 줍니다. 요소 ID 로 지정하게 하니, 화면에 없는 요소를 골랐는지 코드로 바로 확인할 수 있습니다. 에이전트가 "통과"라고 해도 모든 기대결과가 코드 비교로 확인되지 않으면 PASS 가 아닙니다. 에이전트가 통과한 경로는 LLM 없이 도는 pytest + Appium 스크립트로 바꾸고, 팀 코딩 규칙과 로케이터 실재 여부를 검사하는 게이트를 통과해야 실행합니다.

## 데모 결과

`python -m req_ai demo` 결과 요약입니다. 전체는 `out/report.md` 에 있습니다. 가상 앱에는 "할인 금액 앞에 음수 기호가 없는" 결함을 넣어 두었습니다.

```
- 기획 변경 4건 → 요구사항 4건
- 정책 충돌 의심 1건, 기획 확인 질문 3건
- TC 생성 9건 → 채택 8건 (자동 6 / 수동 2), 반려 1건
- 커버리지 누락: 요구사항 1건, 정책 조항 1건
- 기존 스크립트 6개 중 4개 선정 실행
- 결함 의심 1건, 스크립트 갱신 필요 1건
```

데모에서 볼 수 있는 장면:

- **정책 충돌 의심**: "쿠폰 여러 장 적용 시 쿠폰명 모두 표시"(v2 추가) ↔ [CPN-01] "쿠폰은 주문 1건당 1장만" → 기획 확인 요청
- **정책 파생 조건**: 5분 경계(4분 59초 / 5분 1초), 할인 금액 음수 기호 표시, 할인 상한, 결제 금액 0원 미만 금지
- **AI 가 지어낸 것 반려**:
  - 정책서에 없는 조항 [CPN-04] 인용을 제외
  - "주문당 최대 3장"이라고 잘못 인용한 TC 반려
- **누락 표시**: [PAY-02] "결제 금액 0원 미만 불가" 조항을 검증하는 TC 가 없음
- **영향 분석**:
  - 6개 중 S03·S04·S05 를 태그·조항으로 선정
  - S02 는 AI 추천으로 추가 (사유 기록)
  - 등록되지 않은 S09 추천은 무시
- **실패 분류**: S03 은 "가게 확인 중"을 기대하다 실패 → 기획 변경 반영 필요로 분류 (결함 아님)
- **결함 검출**: 정책 조항에서 나온 TC-05 가 "할인 1,000원"(음수 기호 없음)을 FAIL 로 잡음
- **위험 동작 차단**: 주문 취소를 실제로 누르는 TC-09 는 테스트 환경 허용 없이 BLOCKED
- **에이전트 환각 차단**: TC-04 에서 화면에 없는 요소(e15)를 고르자 거부, 다음 단계에서 올바른 요소로 진행
- **스크립트 변환**: 신규 TC 4건을 회귀 스크립트로 바꾸고, 코드 게이트를 통과한 뒤 실행해 4건 모두 통과

## 프롬프트 설계

`prompts/` 에 4종이 있습니다.

| 파일 | 역할 |
| --- | --- |
| `analyze_requirements.md` | 변경 문장 + 관련 조항 → 요구사항, 정책 관계, 파생 조건, 질문 |
| `generate_tc.md` | 요구사항 → 기능 TC + 정책 조항별 경계·예외 TC |
| `impact_suggest.md` | 태그로 안 잡힌 스크립트 중 영향 가능성 있는 것만 추천 |
| `agent_step.md` | 화면 요소 목록을 보고 다음 행동 1개 결정 |

공통으로 지킨 것:

- **출력은 JSON 스키마로 강제**합니다 (tool use 강제 호출). 기능 태그는 스키마 enum 으로 묶어 등록된 값만 쓰게 했습니다.
- **근거와 인용은 "그대로 복사"** 하게 하고, 프로그램이 원문과 대조한다는 사실도 프롬프트에 적었습니다.
- **모르면 질문으로** 남기게 했습니다 (`open_questions`). 기획 리뷰에 바로 가져갈 수 있습니다.
- **충돌은 TC 대신 확인 요청**으로 보냅니다. 정책과 어긋나는 기획으로 TC 를 만들면 틀린 기대값이 자동화에 박힙니다.
- **에이전트는 한 번에 행동 1개**만 정합니다. 여러 단계를 미리 계획하면 중간에 화면이 달라질 때 틀어집니다.

## 실행 방법

```bash
pip install -r requirements.txt

# 1) 데모: 녹화된 LLM 응답 + 가상 앱 (API 키, 단말 필요 없음)
python -m req_ai demo
#   out/report.md                 리포트
#   out/generated/                생성된 회귀 스크립트
#   out/*.json                    변경점, 요구사항, TC, 검증 결과, 에이전트 실행 기록

# 2) 단위 테스트 (LLM 없이 판정하는 부분)
python -m pytest tests

# 3) AI 가 만든 테스트 코드 검증 게이트 (차단 항목이 있으면 종료 코드 1)
python -m req_ai check-code samples/ai_generated/OrderStatusAiTest.java \
    --screens samples/app --package com.sampleapp

# 4) 실제 LLM + 실제 단말
export ANTHROPIC_API_KEY=...
python -m req_ai run --old v1.md --new v2.md --policy 정책.md \
    --registry samples/regression/registry.json --regression samples/regression \
    --device appium --capabilities caps.json --screens 화면덤프폴더 --record replay_new
```

- `caps.json` 은 Appium Inspector 에 넣는 JSON 과 같은 형식입니다.
- `--record` 를 주면 LLM 응답을 저장해 두고 다음부터 같은 결과로 재생할 수 있습니다. 결과가 매번 달라지면 원인 추적이 어려워서 넣었습니다.
- 기존 회귀 스크립트(`samples/regression/`)는 실제 Appium 스크립트입니다. 데모에서는 같은 코드를 가상 드라이버로 돌립니다 (`QA_DEVICE=fake`). 스크립트 코드는 바꾸지 않습니다.

## 한계와 다음 단계

- 데모의 LLM 응답은 녹화본입니다. 실제 모델로 돌리면 문장은 달라지지만, 판정을 코드가 하기 때문에 결과의 구조는 같습니다.
- 시간 경과(주문 후 5분)나 특정 데이터(주문 금액보다 큰 쿠폰)가 필요한 TC 는 지금은 수동으로 분류됩니다. 테스트 데이터 API 를 붙이면 TC 의 사전 조건을 API 호출로 만들어 자동화 대상으로 바꿀 수 있습니다.
- 스크립트 메타데이터는 지금 사람이 관리합니다. 에이전트가 만든 스크립트는 TC 의 태그·정책 조항을 그대로 물려받도록 하면 관리 부담이 줄어듭니다.
- 효과는 다음 지표로 볼 계획입니다.
  - 요구사항당 분석·TC 작성 시간
  - 사람이 승인한 TC 비율
  - 정책 이슈를 개발 전에 찾은 건수
  - 회귀 실행 시간 (전체 대비 선정 실행)
  - 실패 분류가 맞은 비율

## 작업 방식 및 AI 활용

도구의 목적과 흐름은 직접 정하고, 구현과 데모 데이터 작성은 AI 도구(Anthropic Claude)를 활용했습니다.

| 영역 | 담당 | 내용 |
| --- | --- | --- |
| 아이디어·범위 | 본인 | 신규 요구사항 인입 시 내부 정책 기반 분석 → TC 자동 생성 → 변경 영향 스크립트 실행까지 이어지는 자동화로 방향 결정 |
